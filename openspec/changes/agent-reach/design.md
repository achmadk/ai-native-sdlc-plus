# Design

## Context

See [proposal.md](proposal.md) for scope and the `agent-native-bootstrap` and `release-hygiene` deltas for behavior. `scripts/agent_profiles.py` already renders seven profiles from canonical policy, manifest-selected skill files, and five shared operations. Profile selectors, paths, recovery markers, and documentation are maintained in separate places. `tests/test_agent_profiles.py` exercises generation and ownership; it does not launch native loaders.

The current target-profile table in `docs/COMPATIBILITY.md` differs from README and `adapters/README.md`. Repository-self `.claude/CLAUDE.md`, `.cursorrules`, `.cursor/rules/sdlc.mdc`, Copilot instructions, and `GEMINI.md` are separately authored, not owned installation outputs. The two Cursor files differ in both policy and wrapper format; the prompt's byte-identical-file premise no longer holds.

Current release identities are changelog `0.1.1`, doctor `0.3.0`, and wheel `0.0.0.dev0`, with no local tags. The owner selected `0.3.0`, Claude Code plus OpenCode V2 for Level 3, and generation of both Cursor compatibility files. `one-front-door` was archived with its committed proof task incomplete; that warning remains outside this change's ownership.

## Goals / Non-Goals

**Goals:**
- Make profile metadata and adapter generation consistent without changing installed native paths or user ownership.
- Separate static generation, native discovery, and specific observed behavior in version-bound evidence.
- Produce reproducible support and release-readiness outputs without requiring live clients in CI.

**Non-Goals:**
- No additional product skills, agent integrations, provider SDKs, hosted service, runtime sandbox, global settings changes, or silent overwrites.
- No claim that a probe proves broad task quality, every client version, another operating system, or authenticated human identity.
- No repair of archived proof tasks, deletion of legacy adapters, retuning of WS6 evaluations, or remote tag/package publication.

## Decisions

### 1. Extend the existing profile contract, not the framework

Keep one declarative per-profile descriptor in `scripts/agent_profiles.py` for policy mode, native skill prefix, command kind/path/spelling, recovery markers, and negative surface claims. Reuse the existing renderers and `COMMAND_OPERATIONS`; keep the install manifest authoritative for copied skill bytes. Derive CLI selectors and managed-path recognition from the descriptor instead of adding another registry.

Regression tests compare supported selectors, the union of rendered installed paths, recognition, recovery, and full copied-tree bytes for all seven profiles. Keep version-1 installation state, additive profile behavior, direct-edit conflicts, and complete runtime inclusion. A registry refactor must not change previously owned destinations or make old installations unmanageable.

Rejected: a second adapter generator or a generic plugin framework. Existing rendering and ownership already provide the required foundation.

### 2. Separate repository compatibility outputs from installed profiles

Render repository-self adapter files through the same policy/template source, but keep their declared output set distinct from target installation ownership. The named adoption set is `.claude/CLAUDE.md`, `.cursorrules`, `.cursor/rules/sdlc.mdc`, `.github/copilot-instructions.md`, and `GEMINI.md`. Root `AGENTS.md` stays user-owned and is never adopted or rewritten by the generator. Separately authorized policy reconciliation may update it before generation; generation must preserve the approved policy bytes.

Both Cursor compatibility files retain canonical policy content; MDC additionally has its native frontmatter. Compare generated bytes per format and extracted policy content, not entire cross-format file equality. Achmad Kurnianto approved consolidating the reviewed adapter-only safeguards into `AGENTS.md` before adoption, rather than dropping them. Generation requires approval hashes for canonical policy and the current five adapters; ordinary initialization continues to reject differing unowned target files.

Expose a read-only generation/drift check with a bounded output set. Never initialize the source repository over its unowned files to manufacture ownership. Document repository compatibility files separately from the native installed-profile matrix; duplication or precedence under an actual Cursor loader remains evidence to collect, not an assumed success.

Rejected: deleting `.cursorrules` or force-adopting every discovered instruction file. The owner chose retention, and user ownership remains a hard boundary.

### 3. Register a small evidence protocol before native calls

Use a repository-only `scripts/agent_reach.py` harness and versioned records under `evals/agent-reach/`. Commit the registration and fixed criteria before authorized probes. Include profile/surface IDs, client versions to test, candidate SHA, positive/negative fixtures, harmless nonce identity, expected product skill IDs, permitted tool events, repetitions, output/time limits, attempt limits, token/cost policy, and source hashes.

Each result records its level independently, client binary hash/version, platform, exact argv, environment-variable names, generated manifest/policy/skill hashes, controls, terminal result, redaction state, reviewer attribution, and evidence digests. Record actual attempts before invocation, including failures; exact-request caches include candidate, client, fixture, case, and repeat identities. Replaying a completed response is not a new live run.

The ledger is separate from profile metadata. Generation cannot set a native pass. Offline validators check bounded schemas, references, source freshness, completed controls, and expected behavior. Structural validation cannot authenticate a human reviewer or prove an external client was honest; that limitation remains visible.

### 4. Keep the three levels narrow and client-specific

| Level | Accepted evidence | Insufficient evidence |
|---|---|---|
| 1 | Isolated installation, required instruction files, all ten copied skills and declared command formats checked against trusted sources | A renderer function existing without checking its output |
| 2 | Actual native loader output identifies generated scratch skills and paths; negative control excludes the unique project probe | File presence, generic skills scanners, version output, normal filesystem reads |
| 3 | Reviewed native transcript follows fixed behavior after native skill load, with matching negative control and permitted tool events | Provider-catalog classification, a prompted nonce, or another client's transcript |

Target Levels 1 and 2 for all seven profiles; target Level 3 for Claude Code and OpenCode V2. Record one declared client/version/platform combination per target; additional combinations remain unverified until tested. Preserve client boundaries: Copilot VS Code prompt files are not CLI prompts, Gemini CLI is not Antigravity, OpenCode V2 is not Kilo, and Kilo extension and embedded CLI versions are separate facts.

For Level 2, install one profile into a fresh positive scratch project through the trusted initializer and pair it with a negative project. Client-specific discovery may use a documented CLI, API, or retained interactive capture. Verify the installed version's supported mechanism rather than assume Kilo's debug interface exists in OpenCode V2. If no safe native discovery path exists, leave that target blocked.

For Level 3, combine a test-only hidden-nonce loader control with unchanged canonical product-skill loads and three preregistered SDLC behavior cases: lane/evidence routing, preservation of user policy, and honest handling of unavailable proof. Use three repeats and matched negative controls. The probe skill stays outside the ten-skill product catalog. Deny unrelated shell, edit, network, hooks, and MCP tools where the client supports it; otherwise require an explicitly safe capture procedure or block the run. This proves only the registered behavior.

### 5. Isolate native startup and bound all attempts

All client execution requires separate approval for installation, binary/version, authentication, model, permissions, and resource budget. Use disposable homes/configuration, disable updates and plugins/hooks/MCPs where supported, and never dump global settings or credential values into evidence. Treat untrusted project text as data and never let it select executable helpers.

The harness launches fixed client adapters with argv, not shell interpolation. Preserve failures before retrying. A repair to a parser can replay cached responses, but a new client attempt must stay within authorized limits; exhausted or unverifiable budgets stop the run. Runtime and CI remain standard-library-only; live clients are optional verification infrastructure, not gate dependencies.

Rejected: reusing the host's unrestricted coding agent or assuming a zero advertised price authorizes unbounded calls.

### 6. Generate the support matrix from validated records

Generate a deterministic bounded section in `docs/COMPATIBILITY.md` from descriptors plus the result ledger. Include native paths/spelling, required levels, three separate statuses/evidence references, client/version/platform, tested SHA, and limitations. Missing higher-level evidence is explicit. README and `adapters/README.md` link to this table instead of repeating another hand-maintained support matrix.

Tests regenerate the section offline and fail on manual cells, stale hashes, unknown profiles, missing evidence, duplicate IDs, cross-client substitutions, or evidence promotion. Synthetic fixtures test parsers and error branches but cannot certify native coverage. Retain dated evidence and the archived dependency warning rather than rewrite them as current support.

### 7. Unify release identity and preserve chronology

Introduce one small trusted `scripts/version.py` resource for product `0.3.0`, include it in the install manifest/wheel, and make doctor and the wheel builder consume it from their own runtime before freezing the candidate. Do not change schema versions or add another packaging framework. Test wheel filename, METADATA, dist-info, CLI identity, installed resource resolution, and missing-resource failure.

Add a `0.3.0 (Unreleased)` changelog entry for verified accumulated work. Preserve `0.1.0`/`0.1.1` text and dated patch-note claims. Where a patch round's chronology is unknown, describe that uncertainty instead of assigning a guessed date or backfilling tags. The entry becomes a dated release only through an explicit release decision.

### 8. Prepare and tag an exact verified candidate

Add repository-only release preflight with fixed offline checks: clean Git state, canonical identity, valid changelog, complete target evidence, matching runtime/policy/manifest/resource/test hashes, passing verification, coherent wheel metadata, reproducible build hashes, and absent target tag. Reuse verification receipts but extend release-specific input coverage beyond Python files to all shipped resources and adapter policy inputs.

Avoid a recursive receipt SHA: first commit verified code and source inputs, run tests/mutations/doctor and native evidence checks, then commit only declared results and release-note outputs. Preflight records both tested code revision and exact release candidate, requires ancestry and unchanged verified inputs, and rejects any other delta. No newer code is attested by an older receipt.

After two independent human reviews and separate explicit tag authorization, create local annotated `v0.3.0` for the exact candidate and verify its target. Never force, move an existing tag, push it, or publish a package implicitly. Candidate-preparation and tag-creation are distinct tasks, so withheld authorization leaves release acceptance open.

## Risks / Trade-offs

- [Risk] Required clients are absent or have no safe loader surface -> Keep targets incomplete; obtain explicit setup/capture authorization instead of lowering scope.
- [Risk] Global skills or duplicate legacy adapters cause false positives -> Use unique scratch probes, matched negative controls, exact paths, and captured unexpected/repeated loads.
- [Risk] Existing adapter-only rules disappear during generation -> Perform separately approved canonical reconciliation, then bind adoption to policy/adapter hashes; generation never changes canonical policy.
- [Risk] Client startup runs updates or plugins before prompts -> Validate isolation before execution and stop if unsafe behavior cannot be disabled.
- [Risk] Credentials or private project data enter transcripts -> Use synthetic fixtures, allowlisted variable names, bounded secret scanning, and human review before committing redacted records.
- [Risk] Output/version schemas change -> Pin client identity and raw output hashes; reject unsupported formats instead of applying another client's parser.
- [Risk] Passing fixture tests are marketed as native support -> Keep level fields independent and matrix generation dependent on native evidence references.
- [Risk] Release receipts become stale or self-referential -> Separate input and results commits, cover all shipped inputs, and show tested versus tag revision.

## Migration Plan

1. On a new apply request, classify final paths, obtain fresh named Critical approval, and snapshot existing adapters/version/ownership. Do not mark the archived dependency proof complete.
2. Add failing-first registry, full-output, compatibility drift, ownership, record-schema, matrix, version, and release-preflight contracts; implement each group only after meaningful RED evidence.
3. Perform the owner-approved canonical-policy reconciliation, obtain adoption approval for the named repository-self adapters, and implement source-driven regeneration without modifying the approved `AGENTS.md` during generation or unrelated target files.
4. Commit the fixed probe registration and candidate sources with explicit authorization. Validate Level 1 outputs for all seven profiles before native startup.
5. Obtain client-specific setup and probe budgets; collect native Level 2 evidence for all seven profiles and Level 3 evidence for Claude Code/OpenCode V2. Missing tools, controls, records, or review remain blockers.
6. Generate and validate the matrix and final release notes, then run focused/full Windows and WSL suites, mutation, doctor, available ShellCheck, and canonical red-green proof. The `0.3.0` source identity was frozen before probes; keep CI replay offline.
7. Build twice and smoke-test the wheel offline, publish the result-only commit, verify release preflight, and obtain independent human reviews plus explicit authorization for local `v0.3.0`. Record the tag result before closing release tasks.
8. Rollback before tagging by restoring reviewed adapter/version changes and retaining all probe failures as dated evidence. After tagging, do not move the tag: prepare a new corrective release. Remove temporary client configurations, not user configuration, and preserve installation ownership records and canonical policy.
